# Program Doanot Skills

面向 AI 编码代理的通用工程约束技能。

## 概述

`program-doanot-skills` 定义了一组默认的编码纪律，用于降低回归风险、控制复杂度并避免循环失控。  
适用于功能开发、缺陷修复、重构和实现阶段的全过程约束。

## 功能说明

- 保护现有功能与业务逻辑不被新代码破坏
- 强制优先选择更低时间复杂度的实现路径
- 约束循环、重试、轮询与递归必须具备终止条件
- 要求改动最小化、范围聚焦、避免无关修改
- 倡导简单实现，避免过度设计和提前抽象
- 协议/类型定义遵循现有规范，复用已存在结构，保持单一事实来源
- 强化可观测性与可运维性：关键节点与错误路径输出可定位日志
- 遵循 DRY 原则，消除重复代码，提取公共函数和跨模块的公共代码

## 何时使用

在以下场景应启用本技能：

- 开始任何编程任务时
- 修改已有代码路径时
- 引入循环、重试、轮询或递归逻辑时
- 在多个算法方案之间进行复杂度权衡时
- 准备宣布任务完成前进行最终校验时

## 核心规则

1. 不影响现有行为
- 新开发代码不得破坏现有功能。
- 现有业务逻辑必须保持正确运行。
- 交付前必须验证未引入回归。

2. 高性能与低复杂度优先
- 在满足需求前提下选择可行的最低时间复杂度。
- 能用 `O(n)` 就不要用 `O(n log n)`。
- 能用 `O(n log n)` 就不要用 `O(n^2)`。
- 若复杂度升高不可避免，必须明确说明权衡原因。

3. 禁止死循环
- 不得引入无边界、无退出条件的循环。
- 重试、轮询、递归必须具备显式终止条件。
- 必要时加入最大重试次数、超时、`break` 等保护。

4. 手术式修改
- 仅修改完成需求所必需的文件和代码行。
- 不重构无关模块或无关逻辑。
- 除非明确要求，否则保持现有代码风格与模式。
- 仅清理由本次改动引入的无用代码。

5. 保持简单
- 用最小实现满足当前需求。
- 避免为“未来可能”提前增加抽象层。
- 优先清晰直接的实现，而非过度“可扩展”设计。

6. 协议定义遵循现有规范（禁止重复定义）
- 协议定义必须遵循项目已有的协议/规范约定。
- 若某个结构/消息/类型已在别处定义，禁止重复定义。
- 必须复用统一的协议结构，避免更新需要修改两处导致不可维护。

7. 可观测性与可运维性（关键节点打日志）
- 重要流程节点与错误路径必须输出过程日志（如 Redis/数据库/上游接口调用失败）。
- 日志需带关键标识信息便于定位（如 `key`、`user_id`、`request_id`）。
- 禁止打印密钥或敏感内容（token、密码、完整个人敏感信息）。

8. DRY 原则（不要重复代码）
- 不要写重复的代码。如果一段代码或特性被多个地方使用，必须提取出公共函数，遵循模块化和封装性。
- 模块内复用：如果一段代码在一个模块中有两处使用，必须提取出公共的函数调用。
- 跨模块复用：如果一段代码在 2 个以上的模块中有相同的功能（例如生成 jwt token、数据库访问、消息队列发布和订阅、redis 访问等），必须提取出公共代码，供多个模块使用。

## 使用示例

可在任务指令中加入如下约束：

```text
Use program-doanot-skills for this task.
Before coding, ensure no regression risk and choose the lowest practical complexity.
Any loop/retry logic must include explicit termination guards.
```

## 快速检查清单

- 本次改动是否保证了现有功能不受影响？
- 是否选择了当前可行的最低复杂度方案？
- 所有循环/重试/轮询路径是否都能安全终止？
- 改动范围是否仅限于必要文件与必要代码？
- 实现是否足够简单，避免了不必要抽象？

## 边界说明

- 本技能提供的是工程行为约束，不替代具体框架 API 文档。
- 不替代业务需求说明、系统架构设计和完整测试策略。
- 建议与项目级规范（代码规范、提交流程、测试基线）组合使用。
